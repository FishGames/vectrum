# Implementation decisions

Supplements `konzept.md`. Where they differ, this list takes precedence because it is later and more concrete. Numbers are stable identifiers; removed or replaced entries leave gaps. As of: 2026-10-03.

## Fixed requirements

| No. | Decision |
| --- | --- |
| P1 | The mod is public and intended for modpacks. It must run on Fabric, Forge **and** NeoForge. The name "Vectrum" is free. |
| P2 | No mods as prerequisites. Only the Fabric API is allowed. Everything else is an optional integration. |
| P3 | Textures and sounds are supplied separately from the code. Models are simple box shapes and are adjusted by hand when needed. |
| P4 | An **endpoint** is a pipe-like block. Like familiar pipes, it connects to surrounding inventories, theoretically on all 6 sides. |
| P5 | The **digital network** does not bridge dimensions; it is cable-based. |
| P6 | **Wireless** may bridge dimensions with the necessary upgrades. |
| P7 | The coder forms a network of participants. The implementation is chosen so that it stays manageable for large builds as well (see E3). |

## Basic design decisions

| No. | Decision | Rationale |
| --- | --- | --- |
| E1 | **Throughput limit:** Only the endpoint determines it, through its throughput upgrades. Cables do not throttle. The limit is a stored value. A fixed base limit per cable kind can be added later without changing the structure. | Cables have no data and no upgrades. A limit "of the route" would otherwise have to be computed along the path on every transfer. |
| E2 | **Ports:** A network node that borders an inventory is a port (source or target). This applies to cable ends as well as to the endpoint block (see E16, which replaces the earlier wording of E2). Role, filter, priority and mode apply per connected side; upgrades apply per connected side of a cable (E122) and per block for the wireless port. | Operation stays a single GUI with side selection. |
| E3 | **Overview in the digital network:** (1) Coders have a freely selectable name. (2) Coders can be dyed. (3) Clicking a coder or a digital cable with the wrench shows a network overview: a list of all coders with name, colour, location, status and current flow. It shows no contents, so that it does not become a terminal. (4) With the wrench in hand, the whole network is outlined. | A single tool instead of a new block; keeps the rule "one function, at most one block" and does not violate the ban on storage/terminals. |
| E4 | **The wireless port gets upgrade slots**, at least for a new **dimension upgrade**. Concept change: the upgrade table is extended by "dimensions". Digital cables stay without upgrades. | Follows from P6. |
| E5 | **Wireless throughput:** unlimited by default, switchable through a configuration value. | Introducing a limit later is easier than removing it again. |
| E6 | **Main environment Forge.** In 1.20.1, Forge and NeoForge share one platform package (`platform/forge`), Fabric has its own. For energy on Fabric, Team Reborn Energy is bundled (jar-in-jar, E24). | The desired mods (Mekanism, Create, Refined Storage, ...) mostly run on Forge under 1.20.1. |
| E7 | **Core without Minecraft:** Everything under `io.github.fishgames.vectrum.core` imports nothing from Minecraft, Forge, Fabric or Mojang libraries. A test checks this automatically. | The core should be testable without a running Minecraft. |
| E8 | **Coordinates contain the dimension** (`BlockCoord`). The wireless frequency registry is server-wide, all other networks are per dimension. | Keeps P6 open without having to rebuild the core later. |
| E9 | **Redstone** is modelled as a transport type with different behaviour (`SIGNAL`: mirror the value); all other types as `QUANTITY` (transfer an amount). | Avoids special-case code in the core once redstone is added. |

## Item cable and endpoints

| No. | Decision | Rationale |
| --- | --- | --- |
| E10 | **The default role of a port side is input (source).** The wrench cycles the role: input, output, off, input again. Worlds saved before this default are migrated once on load (marker `roleDefault` in `vectrum_networks.dat`): every side of every endpoint of an item, fluid, energy or gas layer without a chosen role is stored as output, so those cables behave as before; redstone is untouched (its default is derived from the neighbour). The side meant is the one with a connected inventory that is closest to the clicked spot (the face directly at the chest cannot be clicked). | An input is the plain arm without a plate, so a newly placed cable is the simplest picture; the output, which needs a deliberate choice, is the one that gets the plate. *Since E115 the roles are named from the block's point of view: what this entry calls input is now shown as output (the block gives out) and the other way round; behaviour and stored values are unchanged.* |
| E11 | **Network membership and port side roles are saved with the world** (`data/vectrum_networks.dat` per dimension) and rebuilt through the core on load. Cables and endpoints have no block entity. | Cables cannot register themselves when a chunk loads. Measured, the rebuild costs about 10 ms for 10,000 blocks. Upgrades, filters and settings live in the same sparse store instead of a block entity per cable. |
| E12 | **Connections are stored in the block state.** Cable: 6 yes/no values. Endpoint: per side none/cable/input/output. Updates happen in `neighborChanged`; neighbours in unloaded chunks are never touched (otherwise chunks would be loaded or connections at the chunk border would be lost). | Model, shape and network read the same state. |
| E13 | **Basic transport:** every 10 ticks each source side hands up to **4** items to the targets in the network, in order of position (both values are configuration entries, E94). The tick runs through Minecraft's scheduled block ticks (no block entity, no loader events). The target list per network is cached and recomputed only when the layer of the network changes (E97). | One cheap, uniform tick for the whole network; the base throughput is 4 items per transfer. |
| E14 | **Access to inventories through its own interface** (`ItemPort`): Forge/NeoForge through the item handler capability, Fabric through the Fabric API's Transfer API. The shared code only knows `moveTo`. | The shared code stays free of loader classes. Fluids, energy and gas use the same pattern (E21). |
| E15 | Cables and endpoints are not waterlogged. Models are simple boxes (P3). | Waterlogging would add a state to every connection state (E12) for no gameplay gain. |
| E16 | **Cable ends take over the endpoint function.** A cable that borders an inventory becomes a port by itself. In the core it then changes from cable to endpoint (`setKind`); a network without such nodes still costs nothing. Cable and endpoint share the base class `ConduitBlock`. | Basic operation without an extra block: lay cables, done. |
| E17 | **The endpoint block is kept** (always active, thicker node). | Cable ends cover the basic function (E16); the block stays as a node with a fixed role. |
| E18 | **Diagnostic tool as its own item** (right click on a cable or endpoint: network number, size, number of inputs and outputs). The wrench is only for configuring. | The detailed diagnostics grow here. |

## Throughput limit

| No. | Decision | Rationale |
| --- | --- | --- |
| E19 | **Throughput limit = one number per port block** (implemented following E1). The limit of a block is its manual value if it has one (`ThroughputLimits` in the core holds only those), otherwise the base amount times the factor of its throughput upgrades (E34); this is one map lookup and one multiplication when transferring, never a computation across the network. Applies to the source (where goods are taken); targets are throttled only by their capacity. A value of 0 stops the block. Manual values are saved with the world (layer `limits` in `vectrum_networks.dat`) and forgotten when the block is broken. | Cables have no data (E1), so the limit can only hang on the port. Deriving the upgrade part keeps the limit correct when the configuration changes, and nothing has to be rebuilt when upgrades change. |
| E20 | **Admin command** `/vectrum throughput <pos> [<value>\|reset]` (operators only): shows, sets or clears a block's limit. The result of the show command is the value (for `/execute store`). The diagnostic tool names the limit of the clicked block. | An exact, scriptable way to read and set the limit. |

## Fluids and energy

| No. | Decision | Rationale |
| --- | --- | --- |
| E21 | **One shared transport for all quantity types.** Access to storage goes through `Port` (`moveTo(target, amount)`), with one implementation per transport type and loader: items (item handler / Transfer API), fluids (fluid handler / Transfer API), energy (Forge Energy / Team Reborn Energy). `Transport.run` only knows the block's type. Units: items in pieces, fluids in mB, energy in FE (1 E of the Team Reborn API = 1 FE). Fabric counts fluids in droplets, converted at the boundary (1 mB = 81 droplets). | Exactly one path for all types. |
| E22 | **Separate cable blocks per type:** item cable, fluid cable, energy cable. Cables of different types do not connect. A cable only recognises storage of its own type as a port (a fluid cable next to a chest does nothing). | Separate cables per type; the universal cable merges them into one block (E39). |
| E23 | **Base amounts per transfer and source side:** items 4, fluids 1000 mB (one bucket), energy 2000 FE (200 FE per tick), gas 1000 mB. Default interval 10 ticks for all types. The values are entries of `vectrum.toml` (E94). | First estimate for a balanced base game; the throughput upgrades raise them. |
| E24 | **Energy on Fabric through Team Reborn Energy 3.0.0** (MIT licence, checked), bundled as jar-in-jar. Fabric has no energy API of its own. | Users need no additional mod for it. |
| E25 | No fluid or energy endpoint block. Cable ends take over the port (E16). | Basic operation needs no extra block. |
| E26 | **Vanilla cauldron as a fluid tank on Forge and NeoForge as well.** Forge has no capability for cauldrons, so there is a dedicated handler (`CauldronFluidHandler`): empty, full water cauldron or full lava cauldron, in whole buckets only (1000 mB). Partially filled water cauldrons (levels 1 and 2) are unusable on Forge, whereas every level works on Fabric (its Transfer API provides third-buckets). | Same behaviour on all loaders, and fluids can be tried out without a third-party mod. |

## Filter, priority, distribution modes

| No. | Decision | Rationale |
| --- | --- | --- |
| E27 | **Routing cascade filter → priority → mode**, implemented in the core (`core/routing`, without Minecraft, with tests). The filter acts on transfer (it checks each concrete good), the priority sorts the targets into groups (higher number first, default 0, negative allowed), the mode distributes within a group. Nothing is lost: only what the target accepts is moved. | Order fixed by the concept. Testable without Minecraft, including randomised tests (sum moved = min(budget, free space) in all modes). |
| E28 | **Settings hang on the port side** (position of the cable/endpoint + side), not on the cable network. `PortSettings` = priority, distribution mode, filter. Only deviations from the default are saved (`PortSettingsTable`, layer `settings` in `vectrum_networks.dat`) and forgotten when the block is broken. Priority and filter apply when the side is a **target**; the distribution mode and the filter apply when it is a **source**. Both filters (source and target) must let a good through. | Cables have no data (E1); as with throughput (E19), a sparse table suffices. |
| E29 | **Filter = whitelist or blacklist over identifiers** (`minecraft:cobblestone`, `minecraft:water`). An empty list lets everything through, regardless of kind. Energy has no kinds and ignores the filter. The identifier comes from the registry, not from the name. There is no NBT distinction (enchanted items etc.) yet. | Simple, language-independent and the same for items and fluids. NBT filters can follow later as an extension. |
| E30 | **Distribution modes:** *sequential* (default: fill the first target, then the next), *round robin* (each transfer starts at the target after the one supplied last; the pointer is stored per source side) and *balanced* (weight = 1 − fill level, at least 0.05; what a target does not accept goes to the others in the next round). The fill level is only queried in *balanced* mode (`Port.fillLevel`). "Round robin" rotates per transfer, not per item. | Covers the usual wishes and stays cheap. |
| E31 | **Back-off for refused targets (approximation of the event register).** If a target accepts nothing although the source holds goods that the filters of both sides let through (`Port.canGive`), the target is asked again only after the pause configured for its number of refusals in a row (default 20, 40, 80, then 100 ticks, `target_pause`). A source that holds nothing is no refusal: it moves nothing and puts no target to sleep. A change of the layer cancels the back-offs of that layer. Back-offs are not saved. | Saves queries when many targets are full. The previous rule (back-off only if the source delivered elsewhere in the same transfer) needed a successful transfer as proof that the source was not empty; `canGive` gives that proof directly, so a lone full target is skipped too. A fully event-driven register (storage reports "free") would need loader events per storage; the price of the pause is a delay of up to the last table entry when a full target has room again. |
| E32 | **Command** `/vectrum port <pos> <side> [priority <number> \| mode <sequential\|round_robin\|balanced> \| filter add\|remove <id> \| filter clear \| filter type whitelist\|blacklist \| reset]` (operators only). Without arguments it shows the settings (result = priority). Unverified identifiers are rejected when adding (neither item nor fluid). Filter and priority are locked by upgrades (E36). | Scriptable access to the settings for operators. |

## Upgrade system

| No. | Decision | Rationale |
| --- | --- | --- |
| E33 | **One upgrade set, five kinds** (`UpgradeType`): throughput, speed, types, filter (max. 1), priority (max. 1). The maximum of the first three is the length of their table in the configuration minus one (default 6, 3, 4; E94). The dimension upgrade was added later (E68). Upgrades belong to a **port** (E122: a side of a cable, the block itself for the wireless port); they are stored in `LevelNetworks` (table `UpgradeTable`, layer `upgrades` in `vectrum_networks.dat`), not in the item and not in a block entity. Only blocks with a connected inventory accept upgrades. | Cables have no block entity (E1); sparse table as with throughput and settings. The maximum counts are first estimates and therefore configurable. |
| E34 | **Effects** (`UpgradeEffects`, pure computation with saturating math): the throughput upgrades multiply the base amount by the table entry of their count (default ×4 per upgrade, up to 4096 times); the speed table gives the interval (default 10, 5, 2, 1 ticks); the types table gives the item types per transfer (default 1 to 5). The upgrades of a block and the values derived from them (interval, types, settings with upgrade gating) are cached per block until the block changes (E101); the throughput is derived from them when read. | Never compute across the network. The factors are in one place, the configuration. |
| E35 | **The type limit applies per transfer to a target.** A type is item plus NBT. Without an upgrade, one type is moved per transfer and target; if the source has several types, they come one after another (the first type in the first slot, until it is empty). Types the target does not accept do not count. Fluids and energy have no type count. | The concept requires it ("more simultaneous item types"). This is a noticeable change compared with the earlier behaviour, in which any number of types arrived at once. The base value can be changed in `UpgradeEffects.BASE_TYPES`. |
| E36 | **Filter and priority are locked by upgrades.** Without a filter upgrade no filter takes effect, without a priority upgrade priority 0 applies. The stored values are kept and take effect again as soon as the upgrade is inserted (`LevelNetworks.effectiveSettings`). The `/vectrum port` command refuses to set them without the upgrade. The distribution mode is not locked (it is not in the concept's upgrade list). | Concept: "options that are not unlocked are not shown"; the command refuses accordingly. |
| E37 | **Upgrade handling:** right-clicking a block with an inventory with an upgrade item inserts one (the action bar reports the state). **Wrench + sneak + right click** removes the upgrades of the clicked side (E122). Upgrades can also be put into and taken out of the slots of the port screen (E123). **Breaking returns all upgrades** (they drop as items). Admin command `/vectrum upgrade <pos> [<side>] [add\|remove <kind> [n]\|clear]` (the side is required for cables) changes them without items (operators only). | Concept: upgrades live in the block, breaking returns everything. |

## Universal cable

| No. | Decision | Rationale |
| --- | --- | --- |
| E39 | **A block can carry several types** (`NetworkBlock.transportTypes()`). The universal cable (`universal_cable`, class `CableBlock` with the type list items, fluids, energy) registers itself in the network of each type as its own node: same position, separate networks, no mixing. The network structure (`NetworkGraph`, layers per type) stayed unchanged. | Required for the universal cable; the core needs no special case (E16 principle "all types run through the same infrastructure"). |
| E40 | **Connections:** A universal cable connects to every network block that carries at least one common type (single cables, endpoints, other universal cables). The networks stay separate: an item cable in the run lets items through, but not fluids. The enabled sides are the same for all types; whether a neighbour in the network of that type really lies there is decided by the graph. | No per-type state in the block state (that would be hundreds of thousands of states); the server graph is the truth. |
| E41 | **Port sides:** The role (output, input, off) applies per side to all types together, and the wrench switches it for all. Which types actually flow at a side follows from what is connected there (chest = items, tank = fluids, machine = what it offers). A type's node is only an endpoint if storage of **that** type lies there. There is no per-side selection of types. | "What flows is decided by the endpoints, not by the cable" (concept), and simpler to operate than separate cables. *Since E115 the roles are named from the block's point of view: what this entry calls input is now shown as output (the block gives out) and the other way round; behaviour and stored values are unchanged.* |
| E42 | **Filters act per type.** A filter only affects types for which it has entries (the entry is in the item or fluid registry, `ResourceFilter.restrictedTo`). A whitelist with only item entries therefore does not block the fluids of the same universal cable. The same holds for single cables. | Otherwise an item filter on the universal cable would block all fluids and the energy. |
| E43 | **Settings apply to the whole block; upgrades per side since E122.** Distribution mode and round-robin pointer are shared; the throughput limit has its own value per type (base value of the type × 4^throughput upgrades). Command: `/vectrum throughput <pos> type <item\|fluid\|energy> [...]`; without a type the first type (items) applies. | One upgrade set for all cables (concept). A shared limit would be meaningless because of the different units (pieces, mB, FE). |
| E44 | **The recipe consumes the single-type cables** (amounts: E82). The diagnostic tool shows each type separately for universal cables. | Concept: the recipe consumes the single-type cables. |

## Redstone

| No. | Decision | Rationale |
| --- | --- | --- |
| E45 | **Redstone is a type with behaviour SIGNAL** (`TransportType.REDSTONE`), its own cable `redstone_cable` (class `CableBlock`, one type). The value of a network is the **greatest signal strength** (0-15) present on one of its input sides; every output side emits exactly this value. Nothing is consumed, no throughput, no upgrades (commands and upgrade item refuse this). The transport tick skips signal types. | Concept: redstone only transmits, processes nothing. |
| E46 | **Event-driven:** When Minecraft reports a change in the surroundings (`neighborChanged`), the network's value is determined anew (`Signals.update`). The neighbours of the outputs are only notified if the output value actually changed, so no loop arises. A tick every 20 ticks is only a safeguard (e.g. after loading the world, because the output values are not saved). | No constant polling; redstone clocks on the cable stay cheap. |
| E47 | **Weak signal only:** Outputs override `getSignal` but not `getDirectSignal`. An output therefore powers lamps, pistons, doors etc. directly and redstone dust next to it, but does not turn blocks behind it into signal sources. | Avoids feedback and special cases; corresponds to a redstone cable, not a redstone block. *Since E115 the roles are named from the block's point of view: what this entry calls input is now shown as output (the block gives out) and the other way round; behaviour and stored values are unchanged.* |
| E48 | **Default roles:** Next to a block that emits signals (`isSignalSource`: lever, torch, redstone block, dust, repeater ...), the side is an **input**, otherwise off. An **output** is chosen by the player with the wrench (or `/vectrum port <pos> <side> role in\|out\|off`). Quantity types keep output as the default. For this, the chosen role is now stored as "not set" (null); old world states load their roles as explicitly chosen. | An output cannot be guessed (lamp, piston, door have no common denominator); an input can. *Since E115 the roles are named from the block's point of view: what this entry calls input is now shown as output (the block gives out) and the other way round; behaviour and stored values are unchanged.* |
| E49 | **The universal cable carries no redstone,** and redstone cables only connect to redstone cables. | The roles are different (input/output instead of source/target). A cable that suddenly emitted signals would be a trap. |
| E50 | **Diagnostics:** For redstone networks the diagnostic tool shows block count, input/output sides and the current signal strength. | The signal strength is not visible on the cable itself. *Since E115 the roles are named from the block's point of view: what this entry calls input is now shown as output (the block gives out) and the other way round; behaviour and stored values are unchanged.* |

## Digital cable and coder

| No. | Decision | Rationale |
| --- | --- | --- |
| E51 | **Digital is its own type with behaviour CONNECTION** (`TransportType.DIGITAL`, `Behavior.CONNECTION`). The digital cable (`digital_cable`, `DigitalCableBlock`) lives only in this layer, transports nothing itself and has no limit, no upgrades, no settings, no tick and no connections to inventories (`portless()`). Commands and the upgrade item refuse it (`acceptsUpgrades()`). | The digital network is only the line between coders; what runs through the coders is determined by the transport networks. The network graph and its tests stay unchanged. |
| E52 | **The coder (`coder`, `CoderBlock`) carries two layers:** all types of the transport network it sits on (items, fluids, energy; a coder next to a universal cable serves all three) and the digital layer. It has no role of its own: the direction follows from the flow. No limit, no upgrades. | Concept: "coder = transition transport network ↔ digital network". |
| E53 | **Coupling through frequencies.** Two coders in the **same digital network** with the **same frequency** couple their transport networks: goods from a source in one network reach targets in the other. The targets of a source = own network + all coupled networks (`LevelNetworks.reachableTargets`, cached by the `epoch()` of network changes). One digital network per dimension. **No relaying:** network A – coder – network B couples A and B; if B is attached to C through another coder with a different frequency, A does not reach C. | Every connection stays visible and predictable (frequency = connection); chains would create random side effects. Relaying could be added later through the cache. |
| E54 | **Frequencies are unbounded integers ≥ 0** (default 0) and are stored per block position in `LevelNetworks` (`CoderLinks`, layer `frequencies` in `vectrum_networks.dat`). Wrench: right click +1, **sneak + right click −1** (the value is shown in the action bar); exact: `/vectrum frequency <pos> [<value>]`. When the coder is broken, the entry disappears. | Concept: "frequency freely adjustable". |
| E55 | **Transport uses the same distribution for cable networks and wireless** (`Transport.distribute`, filter → priority → mode, E19-E36). Targets of other networks carry their dimension (`Target.level`); locked filters and priorities apply as before at the **source sides**. | One path for all, no second set of rules. |
| E56 | **Diagnostics:** For the digital cable, the diagnostic tool shows the digital network (block and coder count, frequencies present); for the coder additionally the frequency and its transport networks. | The digital network is otherwise invisible. |

## Wireless

| No. | Decision | Rationale |
| --- | --- | --- |
| E57 | **The wireless block (`wireless_port`, `WirelessBlock`) sits directly at the storage; a cable is optional (E71).** It has **no block entity**: frequency and modes are stored in a global `WirelessRegistry` (overworld SavedData, `vectrum_wireless.dat`). All blocks with the same frequency belong together; **across dimensions** this needs the dimension upgrade (E68). | Concept; wireless across dimension borders is its added value. |
| E58 | **Mode per type** (items, fluids, energy): send, receive, both, off (`LinkMode`); the default is **receive**. Wrench: right click cycles the mode for all types together, **sneak + right click frequency +1**; exact (also per type): `/vectrum wireless <pos> [mode <type> <mode>]` and `/vectrum frequency`. | A newcomer must not suck out anything they did not knowingly make a source. |
| E59 | **No throughput limit, no operating energy** (constant `WirelessBlock.UNLIMITED`); the concept leaves "limit or unlimited" open, the cost sits in the expensive recipe. The wireless port accepts only the dimension upgrade (E68), no others. Filter, priority and distribution mode per side exist **without an upgrade** (`effectiveSettings(pos, side, free=true)`). | Concept: "frequency + filter without cables, very expensive". A limit could easily be added later. |
| E60 | **Ticking only while a block sends.** A receiver directory per (frequency, type, sender dimension, sender has dimension upgrade) is cached and becomes invalid when the table (`version`), the wireless stamp (`LevelNetworks.stamp`, E97) or 20 ticks (for incomplete lists) change. Receivers in unloaded chunks are skipped; a limited chunk loader setup (e.g. FTB Chunks style) therefore limits the wireless traffic. | No constant running for idle blocks; wireless across far-apart chunks works as long as both sides are loaded. |
| E61 | **The wireless block is not a network block.** Cables next to it do not connect to it, and it serves only the targets of its frequency, not the cable network next to it. It accepts the storage directly on its six sides. | Clear separation: cable = line, wireless = radio. |

## Gas

| No. | Decision | Rationale |
| --- | --- | --- |
| E62 | **Gas is an optional module** (`Modules.gas()`), available on **Forge** and **NeoForge** 1.20.1 (Mekanism 1.20.1 exists for both) and only when Mekanism is loaded; the shared forge code enables it then. On Fabric (no Mekanism) the module stays off and everything else runs unchanged. The switch is set in the Forge entry point **before** `Vectrum.init()` because it determines what gets registered. In `mods.toml`, Mekanism is listed as an **optional** dependency (`ordering="AFTER"`, version range from 10.0). | Concept: "gas only with Mekanism, optional". Without Mekanism the mod must lose nothing. |
| E63 | **Compile-only dependency on the Mekanism API, not reflection:** `modCompileOnly mekanism:Mekanism:<version>:api` from ModMaven, version 1.20.1-10.4.16.80 in `versions/*/gradle.properties` (forge and neoforge). With `-PwithMekanism` the full jar is added as a runtime dependency for test servers. All classes that touch Mekanism live in the package `platform/forge/mekanism` (`MekanismCompat`, `MekanismGasPort`) and are only loaded when the Mekanism mod is present. Used API: `IGasHandler`/`IChemicalHandler` (tanks, insert, extract), `GasStack`, `Action`, `MekanismAPI.gasRegistry()`. | Mekanism chemical tanks only allow extraction on their configured output side and insertion elsewhere, so the mod always uses the capability of the specific side. The API is a small, stable surface, and keeping the classes in one package means Fabric and installations without Mekanism never load them. |
| E64 | **What gas gets:** its own **gas cable** (`gas_cable`, registered only with Mekanism), gas in the **universal cable**, in the **coder** and in the **wireless port** (type `vectrum:gas`, mode per type as with items). Base limit 1000 mB per transfer (like fluids); filter (identifiers from the gas registry, e.g. `mekanism:hydrogen`), priority, modes and upgrades work as with the other quantity types. Unit mB. | Concept. The core already knew the type (`TransportType.GAS`), so only the integration and the registration are new. |
| E65 | **A block with a gas layer needs a gas layer in the network:** Universal cables and coders placed **before** the gas module was enabled have no gas layer yet and must be placed once more (break, place again). New cables and all wireless ports have it immediately. Conversely, if Mekanism is removed again, the world's gas cables disappear (Forge reports unknown entries in the log), everything else stays. | The network nodes are stored with their type list in the world file; an automatic conversion would be too much effort for the rare situation (Mekanism installed later). |
| E66 | **Recipe and loot of the gas cable are in the Forge/NeoForge resources** (`platforms/*/resources/data/vectrum/...`), not in datagen, ; recipes and recipe advancements carry the condition `forge:item_exists` under the key `conditions` (Forge and NeoForge 1.20.1 read that key, not `forge:conditions`), loot tables have no condition support and drop through the item tag `vectrum:drops/<cable>` whose entry is `required: false`. The cable is not in the shovel tag (it is mined without a tool, somewhat slower); name, texture and model always live in the resources. | Datagen runs on Fabric, where the cable does not exist; a recipe, loot table or advancement that names a missing item writes errors to the log. |
| E68 | **Dimension upgrade:** new upgrade type `DIMENSION` (max. 1 per port). It fits the wireless port only (cables and endpoints reject it; the wireless port rejects all other upgrade types). A wireless link between different dimensions works only if **both** the sending and the receiving port carry it; links within one dimension need no upgrade. Right click with the upgrade item installs it, sneak + right click with the item removes it, breaking the port returns it; `/vectrum upgrade <pos> add\|remove dimension` works too. Receiver lists are cached per (frequency, type, sender dimension, sender has upgrade) (E60). Both chunks must be loaded, as before. | Keeps cross-dimension logistics a paid feature (P6, E4). |
| E69 | **Digital cable is 4 px thick, its selection box is 4 px, and 6 px while a cable is held:** the model (core and arms) and the collision shape measure 6..10 px. ## Cable model

| No. | Decision | Rationale |
| --- | --- | --- |
| E90 | **Cables are one solid layer.** Every cable is a single box per part (core, arm); there is no inner box, no second texture and no cutout rendering (`ModBlocks.cables()` and the render-layer registration are gone). Every face of the other cables gets an explicit `"uv": [0,0,16,16]`, so the whole bound texture file is shown regardless of the face's real size; Minecraft's default position-derived crop would show only part of a deliberately designed texture. | E91 | **Cable textures are sized to the cable's real thickness in pixels,** not a fixed 16x16 canvas: 6x6 for the 6 px cables and 10x10 for the 10 px universal cable. `"uv": [0,0,16,16]` always means the whole bound file, scaled to its real resolution, so the model JSON needs no change. | E92 | **The item cable is painted from regions of one 32x32 texture (`item_cable.png`), with pixel coordinates starting at the top left,** and the texture is animated: the file holds 4 frames of 32x32 stacked vertically, `item_cable.png.mcmeta` sets 20 ticks per frame and `interpolate: true` (colours are blended between the frames). The regions below always refer to one frame, so the models are unchanged; instead of one small texture per face. Only the parts the artist has specified exist; everything else stays unpainted. The cable is drawn as a picture seen from the front: the arm to the right of the core shows the region [11,0]-[15,5] as painted (5 px along the arm, core on its left), the arm to the left [0,0]-[4,5] as painted. A core face shows one of 16 regions of 6x6 px depending on which of its four sides (left, right, up, down as seen from the front) have an arm: none, one (4 regions), two (2 straight and 4 corner regions), three (4 regions) or all four; the straight pieces (left and right, or up and down) use [5,0]-[10,5], turned like an arm when the arms are above and below, and all other regions are shown as painted. Arms pointing towards or away from the viewer are not counted, since they cover the face. Every face is looked at from outside and is never mirrored: up is up on the side faces, north is up on the top face and south is up on the bottom face (right = view direction crossed with up). The models are built per direction (`ModModelProvider.itemCableFiles`) without blockstate rotation; for each face the generator (one model per face and arm pattern, `CORE_REGIONS`) searches the face `rotation` that puts the texture axes in the required world directions, using Minecraft's own corner order (`FaceInfo`/`BlockFaceUV`), and fails if none exists (so a mirrored UV can never appear). | The artist specifies what the front picture looks like; deriving every face from that one picture keeps the cable consistent without hand-written tables. | E93 | **Item cable ports: input is a plain arm, output has a plate.** An arm that is linked or an input shows the region of a core without arms ([6,6]-[11,11]) on its end face (it would only be visible if the neighbour did not cover it). ## Runtime performance

| No. | Decision | Rationale |
| --- | --- | --- |
| E97 | **Caches are kept per layer, not globally.** `LevelNetworks` holds one `LayerState` per transport type with the target lists (own, with coder partners, with wireless receivers) by network id, the back-offs and the flow records. A change of a layer clears that layer only; a change of one block (modes, settings, upgrades, severed sides) clears the layers the block belongs to; a change of the digital layer or of a coder frequency clears all layers. Cross-dimension wireless receiver lists are validated against a global counter, `LevelNetworks.stamp()`, which every change raises; only lists that contain wireless receivers look at it. Wireless ports compare the sides that have a storage in `neighborChanged` and clear caches only when those changed. | The former single global counter dropped every cache and back-off of every dimension whenever anything changed anywhere, so a growing base or an active player kept all large networks rebuilding. Layers never depend on each other except through the digital layer. |
| E98 | **A source that moves nothing waits longer.** After 30 ticks without a transfer the wait of the block grows to half the idle time so far, up to `idle_interval_max` (default 40 ticks); the grace is counted in ticks, not in runs, so that a fast source fed in short cycles never waits longer than its interval; any transfer, a neighbour update of the block, a settings or upgrade change, or a wrench action starts again at the regular interval. Applies to cable sources and wireless ports. A scheduled tick cannot be pulled forward, so goods that appear in a waiting source's storage are noticed after at most `idle_interval_max` ticks. | Most sources in a large base are idle most of the time; each costs a port lookup and a slot scan per run. The delay is bounded and configurable. |
| E99 | **Sources are checked before targets are asked.** `Port.canGive(filter)` tells whether the storage holds anything the filter lets through (false is a guarantee, true promises nothing). A source without goods records the attempt and returns; per target with its own filter the combined filter is checked again. The Forge item port reads the occupied slots once per round, remembers refused stacks and per-item filter verdicts during one move, and probes slots only when the storage reports no content (storages that hide their slots). | An empty or non-matching source used to ask every target in range for every run, and each refusal cost a simulated insert. |
| E100 | **Work budget per server tick.** `WorkBudget` starts a clock with the first transfer of a server tick (`time_budget_micros`, default 10000 = 10 ms, shared by all dimensions); once spent, source blocks that have not run yet reschedule themselves for the next tick with high priority, and a block in the middle of a round stops asking targets. A single run is bounded separately (E107). | Scheduled ticks are capped by the game at 65,536 per level per tick but not by time; a base with many sources and a lagging server would otherwise make every tick longer. |
| E101 | **Values derived from a block are cached per block** (`SourceInfo`: upgrades, interval, item types, effective settings per side, filters reduced to a type) and dropped when that block's data changes. The target lists store the filter of their side reduced to the transport type and are grouped by priority once. Worlds saved before throughput limits were derived (marker `limitsManual` missing) lose the stored entries that equal the old derived value (base × 4^count); manual values stay. | The transfer used to rebuild these values on every run (allocations for keys, sets, filter copies). |
| E102 | **A cable checks its connections every `refresh_interval` ticks** (default 100) instead of on every run; changes next to the cable run the check at once through `neighborChanged`. Redstone cables still check on every run. For cables that carry several types, the sides with a storage per type are compared in `neighborChanged` and the layer caches are cleared when they changed. | Re-reading six neighbours and their capabilities on every run was the largest fixed cost of an idle source. Storage that gains a capability without a neighbour update is noticed within the interval. |
| E103 | **Persistence:** round-robin pointers no longer mark the data dirty (a lost pointer only changes who is served first once); settings and pointer tables are indexed by block so that removing a block does not scan every entry; the data is still one file per dimension written when anything else changed. | Every round-robin transfer used to cause a rewrite of the whole file at the next save. |
| E104 | **No asynchronous snapshot/plan/commit.** Planning on another thread needs a copy of every involved storage; the capability access of both loaders and of all other mods is not thread-safe, and the commit on the server thread would still have to verify every move, so little work would leave the server thread for a lot of copying and a loss window in case of a mismatch. Instead the sources are skipped cheaply (E98, E99) and the work is bounded (E100). | Correctness of item movement is a hard requirement (no duplication, no loss); the cost centres (capability lookups, slot reads) are on the server thread anyway. |
| E105 | **Ports are looked up on every run; no handler cache.** Fabric's `BlockApiCache` and capability invalidation listeners on Forge could save the block entity and capability lookup, but they need one cache per looked-up side with its own lifetime and differ per loader. The saving is small compared with the slot reads that follow a lookup, so it is not done. Forge 1.20.1 and NeoForge 1.20.1 have no `BlockCapabilityCache` (it came with NeoForge 1.20.3). | One lookup is a few hash accesses; the slot scan and the simulated inserts are the cost that matters, and E98/E99/E102 reduce how often they happen. |
| E106 | **Blocks start with an offset.** The first tick of a source, a wireless port or a redstone cable is scheduled at the interval plus a number from 0 up to the interval minus one derived from its position (`WorkBudget.phase`). Later ticks keep their phase. | Blocks placed in one go or loaded together would otherwise all run in the same tick, every interval, and make that tick long and the others empty. |
| E107 | **A run has its own time limit.** `run_budget_micros` (default 2000 = 2 ms) limits one run of one source block (all its sides and types, or a wireless port). The ports check `RunLimit` between stacks (Forge item port) or between chunks of 4096 items (Fabric item port) and stop; the goods that are left wait for the next regular run. A run always completes one unit of work, and a stop is not recorded as a refusal of the target. A cable with a very large throughput can therefore lag only itself: it moves less per second under load, its storage backs up, and the tick of the server and the runs of all other cables stay unaffected, because a single run can no longer use up the budget of the tick (E100). Fluids, energy and gas move in one call per target and are not cut. | One source with a huge throughput (a raised table or a manual limit) would otherwise make the server tick as long as its transfer, with every other cable waiting behind it. Throughput gives way to server time. |
| E108 | **Item cable junction box.** Where three or more arms (link, input or output) leave a core and all of them lie in one plane (the two directions across the plane carry no arm), the item cable draws a box around the core: 1 px larger than the cable on every side (4..12 px for the 6 px cable), all six faces showing the region of the plate front ([0,24]-[7,31] of `item_cable.png`) as a picture seen from outside. Three arms in one plane (T), four (cross) and any of the three planes count; two arms (straight piece, corner) and arms in all three axes do not. The generator writes one model `item_cable_junction` and fifteen blockstate parts (three planes times five combinations: the cross and four T pieces), since a blockstate condition cannot count. The box is a picture only: the selection and collision shapes are unchanged, and the core faces below it stay in the model, hidden. Since E120 the fluid, gas and source cables have it too, and it is drawn in the solid colour of the cable. Only the item cable had it at first; the universal cable (10 px) and the digital cable are excluded for now, the other 6 px cables have not been told to get it. | The artist wants a visible junction where lines meet; reusing the plate front keeps it to the one texture that exists for it. *Since E115 the roles are called Pull (what this entry calls input: the cable takes from the block) and Push; since E119 the plate sits on the pull side, so the look described here was swapped. Behaviour and stored values are unchanged.* |

## Roles and energy

| No. | Decision | Rationale |
| --- | --- | --- |
| E115 | **Roles are called Pull and Push, from the block's point of view.** **Pull**: the cable takes from the adjacent block (the block gives out). **Push**: the cable delivers into the adjacent block (the block receives). In the code they are `EndpointMode.SOURCE` (shown as Pull, stored ordinal 1, default) and `TARGET` (shown as Push, ordinal 2); `Connection.SOURCE`/`TARGET` keep the serialized block-state names `in`/`out` of the old naming so that saved cables and models need no migration. Command arguments are `role pull`, `role push` and `role off`. Redstone follows the same rule: a lever is pulled, a lamp pushed. | The earlier names were from the network's point of view and read backwards next to Mekanism and most other mods; "input/output" was still misunderstood, so the plain verbs were chosen. Keeping ordinals and state names means only texts and the command meaning change. The default stays Pull, so a newly placed cable takes from an adjacent inventory (and shows a plate on that side) until a side is set to Push. |
| E116 | **The energy cable pushes and pulls by default, and can be set to pull only.** A side of an energy cable that touches an energy storage cycles Push & Pull (default, plain arm), Pull (plate) and Off (wrench, screen, `role` command; `role push` is the Push & Pull state). On Push & Pull the side both gives and takes energy: in `Transport` such a side is a source side and `LevelNetworks.buildTargets` lists it as a target as well, so the storages decide through `canExtract`/`canReceive` (a generator only gives, a machine only takes). On Pull the side only takes energy out of the block and never delivers into it. The universal cable uses the generic rule (Pull: take only; Push: both ways for energy), so a fresh universal cable pulls energy only until a side is set to Push. | Matches how Mekanism's cables feel (connect a source and a consumer, done), while still allowing a side that must never receive. The existing routing, back-off and work budget are reused; idle sides cost one `canGive` probe and then wait longer (E98). |
| E117 | **Two-way storages are balanced, not ping-ponged.** When both the giving and the receiving energy storage can give and take and both hold energy, the amount of one transfer is limited to what leaves both at the same fill level (`EnergyBalance.limit`); nothing moves from the emptier to the fuller one. A storage that can only give or only take is never limited. | With every side being source and target, two batteries would pass the same energy back and forth every transfer. |
| E118 | **Source of the creative source jar.** `ArsSourcePort` counts a removal from the creative jar as the requested amount, because that jar always reports a full jar and the usual before/after comparison would show nothing taken. | Otherwise a creative jar can never fill another jar through a cable. |
| E119 | **The plate marks Pull, Push is a plain arm; the plate exists on every cable with roles.** The port plate of the item cable (E93) is also drawn on the pull side of the fluid, energy, gas, source and heat cables and of the universal cable: 1 px larger than the cable on every side (8 px for the 6 px cables, 12 px for the universal cable), 2 px deep, in the solid colour of the cable (the plate textures are the cable texture, so no new image files). The push side has no plate; the old green plate is gone. The redstone cable keeps its own look for now (plate on the push side with the item cable texture), the digital cable has no roles. As before, plates are clickable only: the collision shape never contains them (E93). | The plate is the recognisable port; it now means the same on every cable: this side takes out of the block. |
| E120 | **Junction boxes for fluid, gas and source cables.** Where three or more arms leave a core in one plane (E108), the fluid, gas and source cables draw the same box as the item cable (1 px larger than the cable on every side), in the solid colour of the cable. Energy, heat, redstone, universal and digital cable stay without it. The generator marks cables with the `junction` flag in its list. | Ordered by the artist for these cables; the others stay as they are until told otherwise. |
| E121 | **The selection box is core plus arms only.** The outline and the crosshair hit of a cable, endpoint or coder are one box for the core and one plain box per connected side; port plates are not part of it (`ShapeSpec` no longer has plate measures). Which side a click means is decided by the hit position among the port sides (`guiSide`), so it does not depend on the shape. | The plate is 1 px wider than the cable, so the old outline showed a stepped, cluttered silhouette at the end of every pull arm; the artist wants a plain box. |

## Port screen and upgrades per port

| No. | Decision | Rationale |
| --- | --- | --- |
| E122 | **Upgrades belong to a port: one set per side of a cable.** `UpgradeTable` holds seven sets per block: slots 0 to 5 are the sides, slot 6 (`BLOCK`) belongs to the block itself and is used by the wireless port (a single device with the dimension upgrade, E68). Speed, throughput, types, filter and priority of a cable side apply to that side only, so different machines on one cable can be tuned separately. A block ticks at the shortest interval of its source sides; each side keeps a due time (transient, reset when the block changes) and a slower side skips the runs before it is due. The universal cable computes the due time once per run, not per type, so that every type of the side moves in the same run. The type limit and the work budget are taken per side. The throughput limit stays one number per block and type (E19, E43) and is derived from the set of the side that is being served. Wrench and upgrade items act on the side that is clicked (`pickSide`); breaking the block returns the upgrades of all slots. Worlds without a slot tag load the old block-wide set into the `BLOCK` slot; no world with upgrades existed when this was decided, so there is no migration. | Every other mod with upgrades does it per side, and it allows different machines on one cable. The cost is the same as for several ports on one cable: one lookup per source side and run, no work for sides that are not due. |
| E123 | **The port screen has upgrade slots.** One slot per upgrade kind (right column of the screen); the stack size is the installed count, at most the maximum of the kind (`type.maxCount()`). The slots are real menu slots, so the normal click, drag and shift-click handling and the standard slot sync apply; a container listener writes every change to `LevelNetworks` (with a guard so that the write does not echo back) and the screen takes the stored set when it opens or when the port changes. A cable screen shows the slots of the selected side; the wireless port screen shows the block set, which holds the dimension upgrade only. | Hand insertion and removal as asked; no custom slot protocol is needed. |
| E124 | **Redstone mode per port** (`RedstoneMode`: ignore, with signal, without signal; saved with the port settings). The signal is read from the block of the port (`level.hasNeighborSignal`) lazily, only when a mode other than ignore is set. It gates the source sides in `Transport.run` and, through `Target.settings()`, the targets in `Round.move`; a gated side moves nothing. The wireless transport ignores it and its screen hides the button, and redstone cables are outside the transport logic. | Matches the usual machine/cable convention; one signal lookup per gated port and run. |
| E125 | **Port name.** Every port settings object has a name of at most 24 characters (`PortSettings.MAX_NAME_LENGTH`); empty means the default, which is the name of the block's item. It is only shown in the screen (not in tooltips or chat) and copy and paste do not copy it. | Name only in the GUI as chosen; the name belongs to a place, not to a setting set. |
| E126 | **Screen pages.** Every control of the screen is an `EndpointMenu.Element` mapped to a `Page` (`BASIC`, `ADVANCED`) in one table (`LAYOUT`); the gear button opens the advanced page, which has no controls yet and shows a placeholder. Moving a control means changing one line. Copy, paste and the gear are 16x16 icon buttons (`textures/gui/copy.png`, `paste.png`, `gear.png`). The role buttons are Pull, Push and Off (energy cable: Push & Pull, Pull, Off, E116). | The advanced page is meant to take over some basic controls later and to get new ones; the table keeps that cheap. |
| E127 | **Screen data and messages.** The menu view is still a list of int fields as data slots (E74), now with the redstone mode and the name (two characters per field, 12 fields). Name and priority are typed into edit boxes and therefore need messages from the client: `VectrumNet.PORT_NAME` and `PORT_PRIORITY` (Fabric registers server receivers explicitly; Forge and NeoForge share the raw channel). The server clamps the values (priority range, name length) and applies them to the side the menu shows; the priority only takes effect with the priority upgrade, as before (E36). Statistics: the current flow per type and the number of sources and targets of the network, the latter refreshed once per second. | Free text and numbers cannot be sent as button ids; reuse of the existing channel keeps three loaders on one code path. |
