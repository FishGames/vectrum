# Implementation decisions

Supplements `konzept.md`. Where they differ, this list takes precedence because it is later and more concrete. As of: 2026-09-20.

## Fixed requirements

| No. | Decision |
| --- | --- |
| P1 | The mod is public and intended for modpacks. It must run on Fabric, Forge **and** NeoForge. The name "Vectrum" is free. |
| P2 | No mods as prerequisites. Only the Fabric API is allowed. Everything else is an optional integration. |
| P3 | Textures and sounds are supplied separately from the code. Models are simple box shapes and are adjusted by hand when needed. |
| P4 | An **endpoint** is a pipe-like block. Like familiar pipes, it connects to surrounding inventories, theoretically on all 6 sides. |
| P5 | The **digital network** does not bridge dimensions; it is cable-based. |
| P6 | **Wireless** may bridge dimensions with the necessary upgrades. |
| P7 | The coder forms a network of participants. The implementation is chosen so that it stays manageable for large builds as well (see E3). |

## Basic design decisions

| No. | Decision | Rationale |
| --- | --- | --- |
| E1 | **Throughput limit:** Only the endpoint determines it, through its throughput upgrades. Cables do not throttle. The limit is a stored value. A fixed base limit per cable kind can be added later without changing the structure. | Cables have no data and no upgrades. A limit "of the route" would otherwise have to be computed along the path on every transfer. |
| E2 | **Ports:** A network node that borders an inventory is a port (source or target). This applies to cable ends as well as to the endpoint block (see E16, which replaces the earlier wording of E2). Role, filter, priority and mode apply per connected side, upgrades per port block. | Operation stays a single GUI with side selection. |
| E3 | **Overview in the digital network:** (1) Coders have a freely selectable name. (2) Coders can be dyed. (3) Clicking a coder or a digital cable with the wrench shows a network overview: a list of all coders with name, colour, location, status and current flow. It shows no contents, so that it does not become a terminal. (4) With the wrench in hand, the whole network is outlined. | A single tool instead of a new block; keeps the rule "one function, at most one block" and does not violate the ban on storage/terminals. |
| E4 | **The wireless port gets upgrade slots**, at least for a new **dimension upgrade**. Concept change: the upgrade table is extended by "dimensions". Digital cables stay without upgrades. | Follows from P6. |
| E5 | **Wireless throughput:** unlimited by default, switchable through a configuration value. | Introducing a limit later is easier than removing it again. |
| E6 | **Main environment Forge.** In 1.20.1, Forge and NeoForge share one platform package (`platform/forge`), Fabric has its own. For energy on Fabric, Team Reborn Energy is bundled (jar-in-jar); the licence has to be checked first. | The desired mods (Mekanism, Create, Refined Storage, ...) mostly run on Forge under 1.20.1. |
| E7 | **Core without Minecraft:** Everything under `io.github.fishgames.vectrum.core` imports nothing from Minecraft, Forge, Fabric or Mojang libraries. A test checks this automatically. | The core should be testable without a running Minecraft. |
| E8 | **Coordinates contain the dimension** (`BlockCoord`). The wireless frequency registry is kept server-wide later, all other networks per dimension. | Keeps P6 open without having to rebuild the core later. |
| E9 | **Redstone** is modelled as a transport type with different behaviour (`SIGNAL`: mirror the value); all other types as `QUANTITY` (transfer an amount). | Avoids special-case code in the core once redstone is added. |

## Item cable and endpoints

| No. | Decision | Rationale |
| --- | --- | --- |
| E10 | **The default role of a port side is output (target).** The wrench cycles the role: output, input, off, output again. The side meant is the one with a connected inventory that is closest to the clicked spot (the face directly at the chest cannot be clicked). | A new cable end therefore never pulls goods out of a chest unintentionally. |
| E11 | **Network membership and port side roles are saved with the world** (`data/vectrum_networks.dat` per dimension) and rebuilt through the core on load. Cables and endpoints have no block entity. | Cables cannot register themselves when a chunk loads. Measured, the rebuild costs about 10 ms for 10,000 blocks. Later upgrades and filters also belong in this sparse store instead of a block entity per cable. |
| E12 | **Connections are stored in the block state.** Cable: 6 yes/no values. Endpoint: per side none/cable/input/output. Updates happen in `neighborChanged`; neighbours in unloaded chunks are never touched (otherwise chunks would be loaded or connections at the chunk border would be lost). | Model, shape and network read the same state. |
| E13 | **Basic transport:** every 10 ticks each source side hands up to **4** items to the targets in the network, in order of position. The tick runs through Minecraft's scheduled block ticks (no block entity, no loader events). There is no filter, priority or mode yet and no upgrades yet. The target list per network is cached and recomputed only on changes. | Smallest flow that proves the core from start to end. The base throughput is 4 items per transfer. |
| E14 | **Access to inventories through its own interface** (`ItemPort`): Forge/NeoForge through the item handler capability, Fabric through the Fabric API's Transfer API. The shared code only knows `moveTo`. | The shared code stays free of loader classes. Fluids and energy follow later in the same pattern. |
| E15 | Cables and endpoints are not waterlogged yet. Both models are box placeholders, textures are placeholders. | Final models and textures replace the placeholders later. |

| E16 | **Cable ends take over the endpoint function.** A cable that borders an inventory becomes a port by itself. In the core it then changes from cable to endpoint (`setKind`); a network without such nodes still costs nothing. Cable and endpoint share the base class `ConduitBlock`. | Basic operation without an extra block: lay cables, done. |
| E17 | **The endpoint block is kept for now** (always active, thicker node) and later gets a different task and a different name. | To be decided once the task is settled. |
| E18 | **Diagnostic tool as its own item** (right click on a cable or endpoint: network number, size, number of inputs and outputs). The wrench is only for configuring. | The detailed diagnostics grow here. |

## Throughput limit

| No. | Decision | Rationale |
| --- | --- | --- |
| E19 | **Throughput limit = a stored number per port block** (implemented following E1). The `ThroughputLimits` table in the core holds only blocks with their own value; all others have the base limit (4 items per transfer and source side). A single lookup suffices when transferring, never a computation across the network. Applies to the source (where goods are taken); targets are throttled only by their capacity. A value of 0 stops the block. The values are saved with the world (layer `limits` in `vectrum_networks.dat`) and forgotten when the block is broken. | Cables have no data (E1), so the limit can only hang on the port. The throughput upgrades write the same value, so nothing has to be rebuilt. |
| E20 | **Admin command** `/vectrum throughput <pos> [<value>\|reset]` (operators only): shows, sets or clears a block's limit. The result of the show command is the value (for `/execute store`). The diagnostic tool names the limit of the clicked block. | Without upgrades this is the only way to see and try out the limit in game. Stays as an admin tool. |

## Fluids and energy

| No. | Decision | Rationale |
| --- | --- | --- |
| E21 | **One shared transport for all quantity types.** Access to storage goes through `Port` (`moveTo(target, amount)`), with one implementation per transport type and loader: items (item handler / Transfer API), fluids (fluid handler / Transfer API), energy (Forge Energy / Team Reborn Energy). `Transport.run` only knows the block's type. Units: items in pieces, fluids in mB, energy in FE (1 E of the Team Reborn API = 1 FE). Fabric counts fluids in droplets, converted at the boundary (1 mB = 81 droplets). | Exactly one path for all types; redstone and gas follow later as further ports or a special case. |
| E22 | **Separate cable blocks per type:** item cable, fluid cable, energy cable. Cables of different types do not connect. A cable only recognises storage of its own type as a port (a fluid cable next to a chest does nothing). | Separate cables per type; the universal cable later merges them into one block. |
| E23 | **Base limits per transfer and source side:** items 4, fluids 1000 mB (one bucket), energy 2000 FE (200 FE per tick). All types tick every 10 ticks. The values are in `TransportDefaults` and easy to change. | First estimate for a balanced base game; the throughput upgrades raise them. |
| E24 | **Energy on Fabric through Team Reborn Energy 3.0.0** (MIT licence, checked), bundled as jar-in-jar. Fabric has no energy API of its own. This resolves the open point from E6. | Users need no additional mod for it. |
| E25 | No fluid or energy endpoint block. Cable ends take over the port (E16). | The endpoint block gets a different task later (E17). |

| E26 | **Vanilla cauldron as a fluid tank on Forge and NeoForge as well.** Forge has no capability for cauldrons, so there is a dedicated handler (`CauldronFluidHandler`): empty, full water cauldron or full lava cauldron, in whole buckets only (1000 mB). Partially filled water cauldrons (levels 1 and 2) are unusable on Forge, whereas every level works on Fabric (its Transfer API provides third-buckets). | Same behaviour on all loaders, and fluids can be tried out without a third-party mod. |

## Filter, priority, distribution modes

| No. | Decision | Rationale |
| --- | --- | --- |
| E27 | **Routing cascade filter → priority → mode**, implemented in the core (`core/routing`, without Minecraft, with tests). The filter acts on transfer (it checks each concrete good), the priority sorts the targets into groups (higher number first, default 0, negative allowed), the mode distributes within a group. Nothing is lost: only what the target accepts is moved. | Order fixed by the concept. Testable without Minecraft, including randomised tests (sum moved = min(budget, free space) in all modes). |
| E28 | **Settings hang on the port side** (position of the cable/endpoint + side), not on the cable network. `PortSettings` = priority, distribution mode, filter. Only deviations from the default are saved (`PortSettingsTable`, layer `settings` in `vectrum_networks.dat`) and forgotten when the block is broken. Priority and filter apply when the side is a **target**; the distribution mode and the filter apply when it is a **source**. Both filters (source and target) must let a good through. | Cables have no data (E1); as with throughput (E19), a sparse table suffices. |
| E29 | **Filter = whitelist or blacklist over identifiers** (`minecraft:cobblestone`, `minecraft:water`). An empty list lets everything through, regardless of kind. Energy has no kinds and ignores the filter. The identifier comes from the registry, not from the name. There is no NBT distinction (enchanted items etc.) yet. | Simple, language-independent and the same for items and fluids. NBT filters can follow later as an extension. |
| E30 | **Distribution modes:** *sequential* (default: fill the first target, then the next), *round robin* (each transfer starts at the target after the one supplied last; the pointer is stored per source side) and *balanced* (weight = 1 − fill level, at least 0.05; what a target does not accept goes to the others in the next round). The fill level is only queried in *balanced* mode (`Port.fillLevel`). "Round robin" rotates per transfer, not per item. | Covers the usual wishes and stays cheap. |
| E31 | **Back-off for full targets (approximation of the event register).** If a target accepts nothing despite an offer while the source delivered to others in the same transfer, it is asked again after 20, 40, 80, then 100 ticks (5 s). Every change to the network or settings cancels all back-offs. Back-offs are not saved. If the source delivered nothing at all, there is no back-off (otherwise empty sources would put all targets to sleep). | Saves queries when many targets are full. A fully event-driven register (storage reports "free") follows if needed; the price is up to 5 s of delay when a full target has room again. |
| E32 | **Command** `/vectrum port <pos> <side> [priority <number> \| mode <sequential\|round_robin\|balanced> \| filter add\|remove <id> \| filter clear \| filter type whitelist\|blacklist \| reset]` (operators only). Without arguments it shows the settings (result = priority). Unverified identifiers are rejected when adding (neither item nor fluid). The settings are not yet unlocked by upgrades; upgrades and the port screen take over later. | Without an interface, the only way to use and test the functions in game. |

## Upgrade system

| No. | Decision | Rationale |
| --- | --- | --- |
| E33 | **One upgrade set, five kinds** (`UpgradeType`): throughput (max. 6), speed (max. 3), types (max. 4), filter (max. 1), priority (max. 1). The dimension upgrade was added later (E68). Upgrades belong to the **block** (position), not to the side; they are stored in `LevelNetworks` (table `UpgradeTable`, layer `upgrades` in `vectrum_networks.dat`), not in the item and not in a block entity. Only blocks with a connected inventory accept upgrades. | Cables have no block entity (E1); sparse table as with throughput and settings. The maximum counts are first estimates. |
| E34 | **Effects** (`UpgradeEffects`, pure computation with saturating math): throughput ×4 per upgrade (base limit × 4^n, up to 4096 times); speed halves the interval (10, 5, 2, 1 ticks); types allow one more item type per transfer (base value **1**). The throughput is computed once when the upgrades change and stored as the limit (E19); the tick only looks it up. The interval is looked up when the next tick is scheduled. | Never compute across the network. The factors are in one place and easy to change. |
| E35 | **The type limit applies per transfer to a target.** A type is item plus NBT. Without an upgrade, one type is moved per transfer and target; if the source has several types, they come one after another (the first type in the first slot, until it is empty). Types the target does not accept do not count. Fluids and energy have no type count. | The concept requires it ("more simultaneous item types"). This is a noticeable change compared with the earlier behaviour, in which any number of types arrived at once. The base value can be changed in `UpgradeEffects.BASE_TYPES`. |
| E36 | **Filter and priority are locked by upgrades.** Without a filter upgrade no filter takes effect, without a priority upgrade priority 0 applies. The stored values are kept and take effect again as soon as the upgrade is inserted (`LevelNetworks.effectiveSettings`). The `/vectrum port` command refuses to set them without the upgrade. The distribution mode is not locked (it is not in the concept's upgrade list). | Concept: "options that are not unlocked are not shown"; without an interface, the refusal is the substitute. |
| E37 | **Operation until the interface:** right-clicking a block with an inventory with an upgrade item inserts one (the action bar reports the state). **Wrench + sneak + right click** removes all upgrades. **Breaking returns all upgrades** (they drop as items). Admin command `/vectrum upgrade <pos> [add\|remove <kind> [n]\|clear]` changes them without items (operators only). | Concept: upgrades live in the block, breaking returns everything. |
| E38 | Placeholder recipes for the five upgrades (shapeless: marker item + redstone + copper + iron) and placeholder textures. | Superseded by E83. |

## Universal cable

| No. | Decision | Rationale |
| --- | --- | --- |
| E39 | **A block can carry several types** (`NetworkBlock.transportTypes()`). The universal cable (`universal_cable`, class `CableBlock` with the type list items, fluids, energy) registers itself in the network of each type as its own node: same position, separate networks, no mixing. The network structure (`NetworkGraph`, layers per type) stayed unchanged. | Required for the universal cable; the core needs no special case (E16 principle "all types run through the same infrastructure"). |
| E40 | **Connections:** A universal cable connects to every network block that carries at least one common type (single cables, endpoints, other universal cables). The networks stay separate: an item cable in the run lets items through, but not fluids. The enabled sides are the same for all types; whether a neighbour in the network of that type really lies there is decided by the graph. | No per-type state in the block state (that would be hundreds of thousands of states); the server graph is the truth. |
| E41 | **Port sides:** The role (output, input, off) applies per side to all types together, and the wrench switches it for all. Which types actually flow at a side follows from what is connected there (chest = items, tank = fluids, machine = what it offers). A type's node is only an endpoint if storage of **that** type lies there. There is no per-side selection of types yet. | "What flows is decided by the endpoints, not by the cable" (concept), and simpler to operate than separate cables. |
| E42 | **Filters act per type.** A filter only affects types for which it has entries (the entry is in the item or fluid registry, `ResourceFilter.restrictedTo`). A whitelist with only item entries therefore does not block the fluids of the same universal cable. The same holds for single cables. | Otherwise an item filter on the universal cable would block all fluids and the energy. |
| E43 | **Upgrades and settings apply to the whole block.** Speed, types, filter, priority, distribution mode and round-robin pointer are shared; the throughput limit has its own value per type (base value of the type × 4^throughput upgrades). Command: `/vectrum throughput <pos> type <item\|fluid\|energy> [...]`; without a type the first type (items) applies. | One upgrade set for all cables (concept). A shared limit would be meaningless because of the different units (pieces, mB, FE). |
| E44 | **Recipe:** 1 item cable, 1 fluid cable and 1 energy cable + 1 gold ingot yield 2 universal cables (consumes single-type cables, placeholder balancing). The diagnostic tool shows each type separately for universal cables. | Concept: the recipe consumes the single-type cables. |

## Redstone

| No. | Decision | Rationale |
| --- | --- | --- |
| E45 | **Redstone is a type with behaviour SIGNAL** (`TransportType.REDSTONE`), its own cable `redstone_cable` (class `CableBlock`, one type). The value of a network is the **greatest signal strength** (0-15) present on one of its input sides; every output side emits exactly this value. Nothing is consumed, no throughput, no upgrades (commands and upgrade item refuse this). The transport tick skips signal types. | Concept: redstone only transmits, processes nothing. |
| E46 | **Event-driven:** When Minecraft reports a change in the surroundings (`neighborChanged`), the network's value is determined anew (`Signals.update`). The neighbours of the outputs are only notified if the output value actually changed, so no loop arises. A tick every 20 ticks is only a safeguard (e.g. after loading the world, because the output values are not saved). | No constant polling; redstone clocks on the cable stay cheap. |
| E47 | **Weak signal only:** Outputs override `getSignal` but not `getDirectSignal`. An output therefore powers lamps, pistons, doors etc. directly and redstone dust next to it, but does not turn blocks behind it into signal sources. | Avoids feedback and special cases; corresponds to a redstone cable, not a redstone block. |
| E48 | **Default roles:** Next to a block that emits signals (`isSignalSource`: lever, torch, redstone block, dust, repeater ...), the side is an **input**, otherwise off. An **output** is chosen by the player with the wrench (or `/vectrum port <pos> <side> role in\|out\|off`). Quantity types keep output as the default. For this, the chosen role is now stored as "not set" (null); old world states load their roles as explicitly chosen. | An output cannot be guessed (lamp, piston, door have no common denominator); an input can. |
| E49 | **The universal cable carries no redstone,** and redstone cables only connect to redstone cables. | The roles are different (input/output instead of source/target). A cable that suddenly emitted signals would be a trap. |
| E50 | **Diagnostics:** For redstone networks the diagnostic tool shows block count, input/output sides and the current signal strength. Recipe (placeholder): 2 redstone + 1 iron ingot → 6 cables. | Balancing: see E82. |

## Digital cable and coder

| No. | Decision | Rationale |
| --- | --- | --- |
| E51 | **Digital is its own type with behaviour CONNECTION** (`TransportType.DIGITAL`, `Behavior.CONNECTION`). The digital cable (`digital_cable`, `DigitalCableBlock`) lives only in this layer, transports nothing itself and has no limit, no upgrades, no settings, no tick and no connections to inventories (`portless()`). Commands and the upgrade item refuse it (`acceptsUpgrades()`). | The digital network is only the line between coders; what runs through the coders is determined by the transport networks. The network graph and its tests stay unchanged. |
| E52 | **The coder (`coder`, `CoderBlock`) carries two layers:** all types of the transport network it sits on (items, fluids, energy; a coder next to a universal cable serves all three) and the digital layer. It has no role of its own: the direction follows from the flow. No limit, no upgrades. | Concept: "coder = transition transport network ↔ digital network". |
| E53 | **Coupling through frequencies.** Two coders in the **same digital network** with the **same frequency** couple their transport networks: goods from a source in one network reach targets in the other. The targets of a source = own network + all coupled networks (`LevelNetworks.reachableTargets`, cached by the `epoch()` of network changes). One digital network per dimension. **No relaying:** network A – coder – network B couples A and B; if B is attached to C through another coder with a different frequency, A does not reach C. | Every connection stays visible and predictable (frequency = connection); chains would create random side effects. Relaying could be added later through the cache. |
| E54 | **Frequencies are unbounded integers ≥ 0** (default 0) and are stored per block position in `LevelNetworks` (`CoderLinks`, layer `frequencies` in `vectrum_networks.dat`). Wrench: right click +1, **sneak + right click −1** (the value is shown in the action bar); exact: `/vectrum frequency <pos> [<value>]`. When the coder is broken, the entry disappears. | Concept: "frequency freely adjustable". Operation is provisional until the interface exists. |
| E55 | **Transport uses the same distribution for cable networks and wireless** (`Transport.distribute`, filter → priority → mode, E19-E36). Targets of other networks carry their dimension (`Target.level`); locked filters and priorities apply as before at the **source sides**. | One path for all, no second set of rules. |
| E56 | **Diagnostics:** For the digital cable, the diagnostic tool shows the digital network (block and coder count, frequencies present); for the coder additionally the frequency and its transport networks. Recipes (placeholder): quartz + amethyst shard + quartz yield 4 digital cables; coder = universal cable + 2 ender pearls + 2 diamonds + 4 gold ingots. | Balancing in a later step. |

## Wireless

| No. | Decision | Rationale |
| --- | --- | --- |
| E57 | **The wireless block (`wireless_port`, `WirelessBlock`) sits directly at the storage; a cable is optional (E71).** It has **no block entity**: frequency and modes are stored in a global `WirelessRegistry` (overworld SavedData, `vectrum_wireless.dat`). All blocks with the same frequency belong together; **across dimensions** this needs the dimension upgrade (E68). | Concept; wireless across dimension borders is its added value. |
| E58 | **Mode per type** (items, fluids, energy): send, receive, both, off (`LinkMode`); the default is **receive**. Wrench: right click cycles the mode for all types together, **sneak + right click frequency +1**; exact (also per type): `/vectrum wireless <pos> [mode <type> <mode>]` and `/vectrum frequency`. | A newcomer must not suck out anything they did not knowingly make a source. The click mapping is provisional. |
| E59 | **No throughput limit, no operating energy** (constant `WirelessBlock.UNLIMITED`); the concept leaves "limit or unlimited" open, the cost sits in the expensive recipe. The wireless port accepts only the dimension upgrade (E68), no others. Filter, priority and distribution mode per side exist **without an upgrade** (`effectiveSettings(pos, side, free=true)`). | Concept: "frequency + filter without cables, very expensive". A limit could easily be added later. |
| E60 | **Ticking only while a block sends.** A receiver directory per (frequency, type, sender dimension, sender has dimension upgrade) is cached and becomes invalid when the table (`version`), the networks (`epoch`) or 20 ticks (for incomplete lists) change. Receivers in unloaded chunks are skipped; a limited chunk loader setup (e.g. FTB Chunks style) therefore limits the wireless traffic. | No constant running for idle blocks; wireless across far-apart chunks works as long as both sides are loaded. |
| E61 | **The wireless block is not a network block.** Cables next to it do not connect to it, and it serves only the targets of its frequency, not the cable network next to it. It accepts the storage directly on its six sides. Recipe (placeholder, deliberately expensive): nether star + 2 eyes of ender + 2 diamonds + 4 gold ingots yield 2 wireless ports. | Clear separation: cable = line, wireless = radio. |

## Gas

| No. | Decision | Rationale |
| --- | --- | --- |
| E62 | **Gas is an optional module** (`Modules.gas()`), available on **Forge** and **NeoForge** 1.20.1 (Mekanism 1.20.1 exists for both) and only when Mekanism is loaded; the shared forge code enables it then. On Fabric (no Mekanism) the module stays off and everything else runs unchanged. The switch is set in the Forge entry point **before** `Vectrum.init()` because it determines what gets registered. In `mods.toml`, Mekanism is listed as an **optional** dependency (`ordering="AFTER"`, version range from 10.0). | Concept: "gas only with Mekanism, optional". Without Mekanism the mod must lose nothing. |
| E63 | **Compile-only dependency on the Mekanism API, not reflection:** `modCompileOnly mekanism:Mekanism:<version>:api` from ModMaven, version 1.20.1-10.4.16.80 in `versions/*/gradle.properties` (forge and neoforge). With `-PwithMekanism` the full jar is added as a runtime dependency for test servers. All classes that touch Mekanism live in the package `platform/forge/mekanism` (`MekanismCompat`, `MekanismGasPort`) and are only loaded when the Mekanism mod is present. Used API: `IGasHandler`/`IChemicalHandler` (tanks, insert, extract), `GasStack`, `Action`, `MekanismAPI.gasRegistry()`. | The API is a small, stable surface, and keeping the classes in one package means Fabric and installations without Mekanism never load them. |
| E64 | **What gas gets:** its own **gas cable** (`gas_cable`, registered only with Mekanism), gas in the **universal cable**, in the **coder** and in the **wireless port** (type `vectrum:gas`, mode per type as with items). Base limit 1000 mB per transfer (like fluids); filter (identifiers from the gas registry, e.g. `mekanism:hydrogen`), priority, modes and upgrades work as with the other quantity types. Unit mB. | Concept. The core already knew the type (`TransportType.GAS`), so only the integration and the registration are new. |
| E65 | **A block with a gas layer needs a gas layer in the network:** Universal cables and coders placed **before** the gas module was enabled have no gas layer yet and must be placed once more (break, place again). New cables and all wireless ports have it immediately. Conversely, if Mekanism is removed again, the world's gas cables disappear (Forge reports unknown entries in the log), everything else stays. | The network nodes are stored with their type list in the world file; an automatic conversion would be too much effort for the rare situation (Mekanism installed later). |
| E66 | **Recipe and loot of the gas cable are in the Forge/NeoForge resources** (`platforms/*/resources/data/vectrum/...`), not in datagen, with the condition `forge:item_exists vectrum:gas_cable`. Recipe (placeholder): iron ingot + fluid cable + iron ingot yield 2 gas cables. The cable is not in the shovel tag (it is mined without a tool, somewhat slower); name, texture and model always live in the resources. | Datagen runs on Fabric, where the cable does not exist; a recipe without a result item would write errors to the log on all loaders. |
| E67 | **What is tested and what is not:** Tested with real Mekanism 10.4.16.80 on a Forge server and on a NeoForge server (chemical tanks: gas cable transfer with the 1000 mB limit, gas filter, universal cable, wireless port with unlimited transfer), plus the Fabric, Forge and NeoForge builds and the unit tests without Mekanism. Note: Mekanism chemical tanks only allow extraction on their configured output side and insertion elsewhere; the mod uses the capability of the specific side. **Not tested:** Mekanism machines and pipes, radiation, other Mekanism versions, the gas cable in survival play. | Real Mekanism was used for the server tests; the remaining items were out of scope. |
| E68 | **Dimension upgrade:** new upgrade type `DIMENSION` (max. 1 per port). It fits the wireless port only (cables and endpoints reject it; the wireless port rejects all other upgrade types). A wireless link between different dimensions works only if **both** the sending and the receiving port carry it; links within one dimension need no upgrade. Right click with the upgrade item installs it, sneak + right click with the item removes it, breaking the port returns it; `/vectrum upgrade <pos> add\|remove dimension` works too. Receiver lists are cached per (frequency, type, sender dimension, sender has upgrade) (E60). Both chunks must be loaded, as before. | Keeps cross-dimension logistics a paid feature (P6, E4). |
| E69 | **Digital cable is 6 px thick everywhere:** the model (core and arms), the selection shape and the collision shape all measure 5..11 px (the plates for ports do not exist because the cable is portless). | Model, selection box and collision box used to differ (10 px model, 8 px selection, 6 px collision), so the visible cable could not be mined at its edges. |
| E70 | **The coder is a full block:** solid cube model with one texture, shape and collision `Shapes.block()`, opaque (no `noOcclusion`). It still connects to transport cables and digital cables as before; the arm/core/port models are removed. | Matches the wireless port; the coder is a hub, not a cable. |
| E71 | **The wireless port connects to cables and coders.** It is a network block (`NetworkBlock`) and an endpoint in the layer of every quantity type; cables and coders of a type link to it on the sides that face it (wireless ports never link to each other). A **sending** port (per type: send or both) makes all receivers of its frequency reachable for every source in its cable network (and in the networks coupled through coders): the receiving sides at ports plus the targets of the cable network attached to each receiving port. A **receiving** port therefore offers the targets of its own cable network to all senders of the frequency. There is no relaying: the targets of an attached network do not include the wireless links of that network. Duplicates are removed. Throughput of a transfer that starts in a cable is the throughput of the source side as usual; ports themselves stay unlimited for their own storages. Ports placed before this change register their nodes on the next neighbour update or tick (re-placing is the sure way). | The port is modelled on a tesseract: a cable network should be able to feed it and drain it without an extra storage in between. No relaying keeps the result predictable and cheap (one hop, cached per network). |
| E72 | **Redstone defaults:** next to a block that emits signals the side is an input (unchanged); next to a block that reads signals it is an **output**; otherwise off. Readers are recognised by class (lamp, TNT, piston base, command block, repeater, comparator, redstone dust) and by block state property (`powered`, `triggered`, `enabled`: doors, trapdoors, fence gates, rails, note blocks, bells, dispensers, droppers, hoppers). Modded blocks with one of these properties are recognised too. The wrench and `/vectrum port ... role` still override every default. This replaces the "output is never guessed" part of E48. | A new redstone cable should connect to lamps, doors and pistons without a wrench click, as the player expects. |

| No. | Decision | Rationale |

The world side (`world/PortDiagnosis`) only collects the facts (flow records with units/second in `LevelNetworks`, filters through `logistics/Filters`, chunk load state). One code path feeds the diagnostic item, `/vectrum diagnose <pos> [side]`, the GUI, and the Jade/WTHIT/TOP lines. | The rules are unit-testable (`DiagnosisTest`) and every output shows the same answer. |
| E74 | **The endpoint GUI is a vanilla menu without a block entity:** `EndpointMenu` (`AbstractContainerMenu`) opened through a `MenuProvider`; the screen (`EndpointScreen`, 320x224, drawn procedurally, no texture) exists on the client only. Ports have no block entity (E57 for the wireless port, likewise for the cables), so the server computes an `int[]` view of the clicked side and publishes it through `DataSlot`s (two 16-bit slots per value), refreshed every 5 ticks. Every change is a `clickMenuButton` id (role, distribution, filter type, priority steps, clear filter, frequency, link mode per type, side, copy, paste). Right click with an empty hand opens it (a held item keeps its own behaviour: wrench, upgrades, diagnostic tool). The digital cable has no GUI; the coder shows frequency only, the wireless port its link modes. | Vanilla menus need no extra network code and work identically on all three loaders; a `DataSlot` view avoids a block entity. |
| E75 | **Options that are not unlocked are not shown** (no greying): priority and filter rows appear only with the matching upgrade (free on the wireless port, E59), the distribution button only on an input side, the throughput limit line only when a limit exists. The server checks the same conditions again, so a forged button id changes nothing. | Spec: "GUI options not unlocked are not shown". |
| E76 | **Filter with ghost slots:** up to nine ghost slots (menu slots 0..8) list the filter identifiers; clicking a ghost slot with an item in hand adds its identifier, a click without an item removes the entry. A bucket adds the **fluid** identifier when the side has a fluid port but no item port (or on right click); gas identifiers come from JEI/EMI drags. Filter identifiers are validated on the server (`ResourceIds.belongsTo`, type ITEM/FLUID/GAS). Copy/paste keeps one settings snapshot per player in memory (lost on restart). | Ghost slots are the usual convention; a bucket is the natural way to name a fluid without JEI. |

## Recipes and datagen

| No. | Decision | Rationale |
| --- | --- | --- |
| E82 | **Recipe principle:** every kind of connection can be crafted from vanilla materials at any time; its price is one trade-off next to space, limits and range. Single-type cables are cheap (iron, copper, glass, redstone; 6 cables per craft). A block that replaces several parts costs at least the sum of those parts plus a small premium: the universal cable yields **1** cable from one item, fluid and energy cable + 1 gold ingot (was 2, which made it cheaper than three separate lines). The digital cable stays 2 quartz + 1 amethyst shard for 4, the coder 4 gold + 2 diamonds + 2 ender pearls + 1 universal cable, the wireless port (2 per craft) nether star + 2 eyes of ender + 2 diamonds + 4 gold. Digital connections and wireless links need two blocks per connection, so the price of a link is twice the block. Replaces the yield in E44 and the placeholder balancing of E38 and E43-E61 for these blocks. | Nothing is locked behind progression; each option has its own advantages and drawbacks. |
| E83 | **Upgrades are ring recipes** (shaped, 1 per craft): metal in the four corners, redstone at the four sides, the marker item in the centre. Throughput: iron + hopper. Speed: copper + clock. Types: iron + chest. Filter: copper + paper. Priority: copper + gold ingot. Dimension: diamonds in the corners, gold ingots at the sides, an eye of ender in the centre (the most expensive one; at most 1 per wireless port). Unlock advancement: having the corner metal. | Stackable upgrades (throughput up to 6, speed 3, types 4) cost real resources, the one-off filter/priority upgrades stay cheap, the dimension upgrade is the most expensive. Replaces the shapeless placeholders of E38. |
| E84 | **Datagen writes every model and blockstate of cables and cubes.** `ModModelProvider` generates blockstate, core/arm/in/out/inventory models and item model per cable (10 px thick; the digital cable 6 px, E69), including the gas cable although it only exists with Mekanism (its recipe and loot table stay in the platform resources, E66); coder and wireless port are cube blocks (`cubeBlock`); plain items get `item/generated` models. Only the item endpoint still has hand-written files (its own shape). The generated files were compared with the old hand-written ones (all 63 files identical) before those were deleted. New item tags `vectrum:cables` and `vectrum:upgrades` (gas cable optional) are for modpack recipes and datapacks. | One place to change a cable shape or add a cable; no drift between eight copies of the same JSON. |
| E85 | **The template example item and example block are removed** (registration, recipes, loot table, tag entries, models, textures, translations). | They were scaffolding from the project template and would show up in the creative tab of a public release. |

## Cable severing

| No. | Decision | Rationale |
| --- | --- | --- |
| E86 | **A link side can be manually severed and reconnected with the wrench.** Right click a `LINK` side severs it; a severed side shows as `NONE` (no arm, no port) and no longer joins the two networks there. Right click the same side again reconnects it. The flag lives in `LevelNetworks` as a per-block, per-side bit mask (`severed`, mirrors the frequency storage), is set symmetrically on the matching neighbour when there is one, and is cleared when the block is removed. Setting it forces a block-state change, which runs through the existing place/neighbour-update path that already keeps the network graph in sync, so no extra graph code was needed. Applies to every `ConduitBlock` that uses the base `onWrench` (all cables, the digital cable); the coder overrides `onWrench` for its frequency and is unaffected. | Two lines of the same type placed directly next to each other always link automatically; this lets them run side by side without merging, one touching side at a time. |
| E87 | **What is tested and what is not:** Tested on a real dedicated server: two three-segment item-cable lines placed directly next to each other merge by default (items cross from one line into the other); severing every touching side splits them into two independent networks (no more crossing); reconnecting restores the merge; the severed state (block state and item flow) survives a world save and reload; breaking a severed cable and placing a new one there relinks it. The sever/reconnect step itself was driven through a temporary RCON test command that calls the same `LevelNetworks`/`refresh` code path as the wrench, not through an actual in-world right click. **Not tested:** the actual wrench right click and its action-bar messages in a real client, the digital cable and gas cable with this feature, Forge and NeoForge (only Fabric was used for this check). | The graph and persistence logic is the risk here and was checked end to end; a literal mouse click was out of scope for this pass. |

## Placement shape

| No. | Decision | Rationale |
| --- | --- | --- |
| E88 | **Single-type cables (item, fluid, energy, redstone, gas) are 6 px thick** (model and collision shape both 5..11 px, matching the digital cable, E69) instead of 10 px. Their **placement/interaction shape** (`getShape()`, decides what the crosshair hits: opening the port screen, the wrench, and targeting through or against the cable while placing or breaking something else) stays at the old 10 px (3..13 px) while the player holds the wrench, a cable item, a coder or a wireless port, and shrinks to the same 6 px as the model the rest of the time (empty hand included). Held item is read from `CollisionContext.isHoldingItem`, which the game already fills in with the clicking entity for this exact shape lookup (confirmed by reading the decompiled `ClipContext`/`EntityCollisionContext` classes; the same mechanism vanilla uses for pointed dripstone). The universal cable and the digital cable are unchanged (fixed 10 px respectively 6 px, no dynamic shape); `ConduitBlock` still supports a fixed shape for them by passing no expanded spec. | Thin cables everywhere looked repetitive and a purely thin cable is fiddly to click precisely; widening the target only for items that are actually used to build or edit the network keeps building near cables (empty hand, unrelated items) from being blocked by an oversized invisible hitbox. |
